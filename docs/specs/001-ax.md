# ax — Agent Exchange CLI

## Spec v1.0

---

## Motivation

Software engineers increasingly use coding agents like Claude Code and Codex as primary development tools. A typical workflow involves a chain of prompts leading to a spec, then a plan, then an implementation. At each stage, the engineer reviews the agent's work manually.

A natural improvement is to delegate the review step to a second agent. Rather than the engineer reviewing Claude's implementation, they could ask a Codex agent to review it, receive structured feedback, and have Claude iterate based on that feedback — all while the engineer watches and retains the ability to intervene.

Today, there is no lightweight mechanism for coding agents to communicate with each other. Each agent runs in its own terminal, unaware of the other's existence. Orchestrating them requires the engineer to manually copy context between terminals, which defeats the purpose of using agents in the first place.

---

## Problem Statement

An engineer wants to run multiple coding agents in parallel, have them communicate with each other (e.g., request reviews, share feedback, coordinate work), and observe the entire interaction without building custom infrastructure or losing control of the workflow.

There is no existing tool that provides this. tmux provides the multi-pane terminal environment, and each coding agent has its own CLI, but there is nothing bridging them — no discovery, no messaging, no session management.

---

## Vision

`ax` (Agent Exchange) is a lightweight CLI that enables coding agents running in tmux panes to discover each other and exchange short messages. It provides session management, agent registration, and message delivery — nothing more. It is the thinnest possible coordination layer between agents that already know how to do their jobs.

The design philosophy:

- **tmux is the runtime.** Every agent participant is a tmux pane. tmux provides the visual multiplexing, the process isolation, and the human's ability to observe and intervene.
- **Keystrokes for signals, files for content.** Agents communicate rich information (specs, plans, review feedback) through files in a shared directory. `ax` only delivers short signal messages ("review ready, see file X") by injecting keystrokes into the target agent's tmux pane — exactly as a human would.
- **The human is always in control.** The engineer starts sessions, can watch all panes, can type into any pane to intervene, and can manually join or restart agents. `ax` never runs autonomously or makes decisions.

## Requirements

### Session Management

- The engineer must explicitly initialize an `ax` session before starting any coding agent. This is a human-only action.
- `ax init` must start a tmux session if the engineer is not already inside one, then enter it.
- `ax init` must generate a unique session ID and set it as a tmux session-level environment variable (`AX_SESSION_ID`) so that all panes within the tmux session inherit it.
- `ax init` must create the session's directory structure under `~/.local/state/ax/sessions/<session-id>/`, following the XDG Base Directory Specification for application state. This location may be overridden via an `AX_STATE_DIR` environment variable.
- Multiple sessions may coexist (e.g., one for frontend work, one for backend work). Each session has its own isolated directory and registry.

### Agent Registration

There are two paths for an agent to join a session:

**Self-registration (`ax join`)** — for agents that are already running in a tmux pane. The engineer starts a coding agent manually, and the agent (or the engineer) runs `ax join` to register that pane into the current session. This is the path used by the first agent in a session.

- `ax join` must read `AX_SESSION_ID` from the tmux environment to determine which session to join.
- `ax join` must accept a `--role` flag (e.g., `implementer`, `reviewer`, `architect`) and a `--label` flag (e.g., `claude-1`, `codex-1`).
- The label must be unique within the session. If the label already exists, `ax join` must update the existing entry with the new pane ID (supporting the case where an agent is restarted in a new pane and re-registers under the same label).
- `ax join` must capture the current pane's unique tmux pane ID (`%N` format) and write it to the session registry.

**Spawning (`ax spawn`)** — for agents brought in by other agents. One agent decides it needs a reviewer and spawns it.

- `ax spawn` must create a new tmux pane, register the new agent into the session registry, and only then start the specified command in that pane.
- The ordering is critical: the new agent must be discoverable in the registry before its process starts, so the spawning agent can immediately send it messages without race conditions.
- `ax spawn` must accept `--role`, `--label`, and a command string.
- `ax spawn` must accept a `--layout` flag to control initial pane placement. Supported values: `hsplit` (horizontal split, new pane to the right), `vsplit` (vertical split, new pane below), `window` (new tmux window/tab). The default must be `hsplit`.
- For layout requirements beyond what `--layout` provides (e.g., specific pane sizes, moving a pane to a different window, swapping pane positions), agents should use tmux CLI commands directly after `ax spawn` completes. Pane IDs (`%N`) are stable across rearrangement operations, so the session registry remains valid after any tmux layout change. The `--help` output for `ax spawn` must document this pattern explicitly so that agents know to use `ax spawn` for creation and tmux directly for rearrangement.
- `ax spawn` must configure the new pane to close when the agent process exits (`remain-on-exit off`), so that dead panes are not mistaken for live agents.

### Discovery

- `ax who` must list all agents registered in the current session, showing their label, role, pane ID, and status.
- `ax who --role <role>` must filter the listing to agents with the specified role.
- `ax whoami` must report the current pane's label, role, session ID, and pane ID.
- Discovery must be based on pane ID lookup: an agent determines which session it belongs to by reading `AX_SESSION_ID` from the environment, then looks up its own pane ID in that session's registry.

### Messaging

- `ax send <label> "message"` must deliver a short text message to a specific agent by injecting keystrokes into its tmux pane.
- `ax send --role <role> "message"` must broadcast the message to all agents in the session with the specified role.
- Before sending, `ax send` must verify that the target pane still exists. If the pane is gone (agent crashed or was closed), `ax send` must update the registry to reflect the agent's status and return a clear error.
- Messages are short signal strings (comparable to an SMS), not large payloads. All substantive content (specs, plans, reviews) must be communicated through files in the session directory.
- `ax send` must wrap the raw message in a structured format before injecting keystrokes, so the receiving agent can identify the sender and the protocol. The delivered message must follow this format: `[ax sms from <sender_label> (<sender_role>)]: <message>`. For example, if `claude-1` (role: `implementer`) sends the message `"review complete, see responses/002.md"` to `codex-1`, the keystrokes injected into codex-1's pane must produce: `[ax sms from claude-1 (implementer)]: review complete, see responses/002.md`. The `ax sms from` prefix serves as a recognizable marker that agents can be taught to look for via their skill definitions.

### Directory Structure

Each session must maintain the following directory structure:

```
~/.local/state/ax/sessions/<session-id>/
  registry.json       # Agent registry (labels, roles, pane IDs)
  comms/              # Files exchanged between agents
    claude-1/         # Files written by claude-1
    codex-1/          # Files written by codex-1
```

Each agent gets its own subdirectory under `comms/`, created automatically when the agent registers via `ax join` or `ax spawn`. Agents must write their files (reviews, specs, feedback, etc.) into their own `comms/<label>/` directory. The naming and structure of files within each agent's directory is not specified by `ax` — it is defined by the skills/prompts injected into each coding agent and may evolve independently of `ax`.

### Skill Generation

- `ax skill` must output a universal `SKILL.md` file to stdout that can be installed into any coding agent's skill directory.
- The skill file must document: the full `ax` CLI interface (all commands, flags, and their behavior), the message format (`[ax sms from <label> (<role>)]: <message>`), the session directory structure and conventions for the `comms/` directory, and how to discover other agents in the session.
- The skill file must be agent-agnostic and role-agnostic. It teaches the agent how to use the `ax` protocol, not how to behave in a specific role. Role-specific behavior (e.g., how a reviewer should conduct a review) is the engineer's responsibility to layer on separately.
- The intended usage is: `ax skill > ~/.claude/skills/ax.md` (or the equivalent skill directory for other coding agents).
- The skill content must stay in sync with the CLI — it is generated from the same source of truth as `--help`, not maintained as a separate document.

## CLI Reference

```
ax init
ax join --role <role> --label <label>
ax spawn --role <role> --label <label> [--layout hsplit|vsplit|window] "<command>"
ax send <label> "message"
ax send --role <role> "message"
ax who [--role <role>]
ax whoami
ax skill
```

Eight commands total. `ax init` and `ax skill` are human-only. All other commands may be used by agents or humans.

## Design Decisions

### Why tmux as the runtime

Coding agents are terminal applications. tmux provides multi-pane terminal multiplexing, process isolation, and — critically — the ability for the human to observe all agents simultaneously and intervene by typing into any pane. No custom UI or dashboard is needed.

### Why keystrokes for signals instead of polling

An alternative design would have agents poll the filesystem for incoming messages (using `inotifywait` or periodic checks). Polling consumes agent turns, which costs money in API-call-based agents. Sending keystrokes via `tmux send-keys` is free and mirrors exactly how a human would orchestrate two agents manually.

### Why file-based content exchange instead of keystroke payloads

`tmux send-keys` is fragile for anything beyond short strings. Multi-line content, special characters, shell metacharacters, and long payloads all create escaping problems. Files are inspectable, debuggable, and can carry arbitrarily complex content.

### Why `~/.local/state/ax/` for session data

The XDG Base Directory Specification defines `~/.local/state/` as the standard location for application runtime state — data that is meaningful while the application is running but disposable afterward. Session registries fit this definition. Storing sessions here rather than in the project working directory avoids polluting project trees and `.gitignore` files, and keeps session data centralized regardless of which directory agents are working in. The location is overridable via `AX_STATE_DIR` for custom setups.

### Why session-scoped isolation

Multiple agent groups may operate in the same project simultaneously (e.g., frontend and backend teams). Session-scoped directories and registries ensure that agents in one group never interfere with agents in another, even if they share the same working directory.

### Why `ax join` and `ax spawn` are independent operations

`ax join` handles self-registration for agents already running. `ax spawn` handles creation and pre-registration of new agents. They are not layered (spawn does not call join internally) because spawn must register the agent before starting its process, while join registers an already-running process. The timing guarantees are different.

### Why `ax join` performs upsert on existing labels

If an agent crashes and is manually restarted in a new pane, the engineer can run `ax join` with the same label to update the registry with the new pane ID. This avoids the need for a separate "rejoin" or "re-register" command.

### Why pane IDs (`%N`) instead of pane indices

tmux pane indices change when panes are rearranged, closed, or swapped. Pane IDs (`%0`, `%1`, etc.) are globally unique and stable for the lifetime of the tmux server. `ax` always uses pane IDs internally.

### Why Go with Cobra

`ax` compiles to a single static binary with zero runtime dependencies. Cobra provides well-structured `--help` output for every command and subcommand. Since coding agents discover how to use tools by running `<tool> --help`, high-quality help messages reduce the need for detailed prompting in agent skill files. The `bitfield/script` library is recommended for ergonomic shell command execution within the Go codebase, since nearly all `ax` operations involve invoking `tmux` CLI commands.

### Why not lazy initialization

An earlier design allowed agents to implicitly create sessions on first use. This was removed in favor of explicit `ax init` by the human. The human should always establish the workspace intentionally before agents begin operating. This provides a clear boundary: the human sets up the environment, agents work within it.

## Out of Scope (v1)

The following were considered and explicitly deferred:

- **Session resume.** Saving agent session IDs and resuming an entire `ax` session after a tmux restart. Deferred until the core flow is validated and the resume semantics of each coding agent are better understood.
- **Workflow orchestration.** `ax` is a communication primitive. It does not track tasks, dependencies, or workflow state. All coordination logic lives in the skills/prompts injected into each agent.
- **Message acknowledgment or delivery guarantees.** `ax send` is fire-and-forget. If the target pane is gone, it reports an error. It does not retry, queue, or guarantee ordering.
- **Agent-specific integrations.** `ax` does not know about Claude Code, Codex, or any specific agent. It operates on tmux panes and labels. Agent-specific behavior (how to request a review, how to format feedback) is defined in each agent's skill files, not in `ax`.
